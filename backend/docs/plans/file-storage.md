## 1. F3：批量打包下载

```http
GET /api/v1/files/archive?thread_id=t_20261102_xxx
```

返回 zip。**为什么需要**：agent 改完一个项目有几十个文件，用户要的是"打包
下载"，不是一个一个点。

用**流式 zip**（`zipfile` 边写边输出），不把整个 zip 读进内存 —— 工作区
可能有几百 MB。

实现要点：

- 只打**工作区里的东西**，`.artifacts/` 不在内（里面有对话历史）；
- `ZipFile` 直接挂在 `StreamingResponse` 的写入流上，或者边生成边 yield；
- 单个文件超过上限时跳过并记日志，不要让整个包失败。

---

## 2. F4：工作区容量上限 + 兜底回收

工作区目录会无限增长 —— agent 生成的产物一直堆着。

| 方案 | 说明 | 结论 |
| --- | --- | --- |
| A. 等会话管理模块 | 清理挂在"删除会话"上，语义最对 | 要等会话管理做完 |
| B. 定时清理 | 按 `mtime` 清理 N 天没动过的工作区 | **单独做是危险的** |
| C. 容量超限兜底 | 工作区目录数/体积超上限时，按 `mtime` 回收最老的 | **要做这个** |

> ⚠️ **B 单独做是危险的** —— 用户可能两周没碰某个会话，但文件还要用。
> 时间不是"用户不再需要"的可靠信号。**容量超限才是。**

做法跟容器容量上限（`sandbox_max_containers`）同一套思路：统计各工作区的
体积，超了就从最久没动的开始回收。

注意：**回收工作区不等于回收容器** —— 容器是执行环境，工作区是文件，两者
的生命周期要分开算。

## 3. F5：会话删除联动清理

平台**现在没有会话管理模块** —— 没有会话表，也没有"删除会话"这个动作。
文件的生命周期挂在会话上，所以这条暂时挂不上。

要做的话是三件事：

1. 加 `conversation` 表 + 增删改查接口；
2. 删除会话时调 `MemoryService.forget_thread`（清短期记忆）；
3. 同时删掉这个会话的工作区目录与 `.artifacts/` 目录。

## 4. 还没解决的更大问题

### 4.1 没有鉴权（上线前的硬门槛）

文件接口是**裸奔**的 —— 知道 `thread_id` 就能：

- 上传文件到别人的会话（塞东西）
- 下载别人会话里的**所有文件**（含用户的需求文档、agent 改的代码）
- 删除别人会话的文件

`thread_id` 由客户端生成，泄露即等于交出整个工作区。

这是"记忆接口无鉴权"那条风险的更严重版本 —— 那里泄露的是"用户偏好"，
这里是"用户的文件"。**上线前必须补。**

### 4.2 base64 驻留 checkpoint

内联的图片会进 `state["messages"]`，被 checkpointer 持久化 —— 多轮对话里
每张图都占一份，checkpoint 会明显变大。

deepAgents 的 `offload_binary_content` 能解决，但 `create_deep_agent` 不暴露
这个参数，要开就得自己构造 `FilesystemMiddleware` 顶替它，漏传 `permissions`
会**破坏审批链路**。

暂时靠限制体积兜着（单图 ≤ 5MB、一轮 ≤ 10 个附件）。详见实现文档 §6。

### 4.3 上传件 agent 能改

用户拿不回原件。上传接口返回 sha256 与原始文件名，让用户知道传的是什么。
**要不要给上传件加"只读"标记** —— 第一版没做（用户就是让 agent 改它，
是正常需求）。
