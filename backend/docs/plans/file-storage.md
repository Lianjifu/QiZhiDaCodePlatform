# 文件存储方案（上传 / 输出）

> 状态：**方案已定，待实施**（2026-11-02）
>
> 关联文档：[implementation/backend-strategy.md](../implementation/backend-strategy.md)（后端存储，已实现）、
> [implementation/context-module.md](../implementation/context-module.md)（上下文模块，已实现）、
> [implementation/memory-module.md](../implementation/memory-module.md)（记忆模块，已实现）

平台现在**完全没有文件的上传与下载接口** —— 用户给不了文件，也拿不走 agent
产出的东西。本方案补上这两头。

---

## 0. 结论速览

| 面 | 结论 |
| --- | --- |
| 三类文件 | **上传件 / 工作产物 / 平台产物** —— 存储位置、生命周期、可见性都不同 |
| 上传件 | 落**会话工作区**的 `uploads/` 子目录 —— agent 立刻能用现有文件工具读 |
| 工作产物 | 就在**会话工作区** —— agent 写在哪就在哪，不另设一套 |
| 平台产物 | `.artifacts/`（工作区外）—— 对话历史外置、大工具结果；**agent 看不见** |
| 下载 | 只暴露**工作区**的内容（上传件 + 工作产物）；平台产物不给下载 |
| 保留期 | 跟着会话走 —— 会话删了，文件一起没 |
| 前置 | **会话管理模块**（当前缺失）—— 文件的生命周期挂在会话上 |

---

## 1. 现在缺什么

| 能力 | 现状 |
| --- | --- |
| 用户上传文件 | ❌ 完全没有接口 |
| 用户下载文件 | ❌ 完全没有接口 |
| agent 看到上传的文件 | ❌ 没有上传就没有文件 |
| 大产物的下载 | ❌ 没有 |

deepAgents 的 `upload_files` / `download_files` **不是这个** —— 那是 backend
协议里的内部机制（blob 外置、媒体外置、技能加载、对话历史外置），模型和用户
都用不到它。

---

## 2. 三类文件：先分清

混在一起谈会得出错误的设计。三类的**存储位置、生命周期、谁看得见**都不同：

| | 上传件 | 工作产物 | 平台产物 |
| --- | --- | --- | --- |
| **谁产生** | 用户 | agent | 框架（deepAgents） |
| **例子** | 需求文档、报错日志、数据集 | 改好的代码、生成的报告、图表 | 对话历史外置、大工具结果 |
| **存在哪** | 工作区 `uploads/` | 工作区（agent 写哪就在哪） | 工作区外的 `.artifacts/` |
| **agent 看得见** | ✅ 读 | ✅ 读写 | ❌ 故意看不见 |
| **用户能下载** | ✅ | ✅ | ❌ |
| **生命周期** | 跟会话 | 跟会话 | 跟会话（容器回收时另算） |

### 2.1 为什么平台产物不给下载

`.artifacts/` 里有：

- `conversation_history/` —— **被压缩掉的对话历史**，含用户说过的话；
- `large_tool_results/` —— 太大塞不进上下文的工具输出；
- `blobs/` —— 二进制内容外置。

前两个是**内部机制**，不是给用户的产物。尤其是对话历史 —— 那是隐私内容，
暴露成下载接口等于开了个泄漏口。

> ⚠️ 这条也正是我们把 `artifacts_root` 指到工作区**外面**的原因（见
> [backend-strategy.md](../implementation/backend-strategy.md)）。它对 agent 不可见，
> 对用户也不可见。

### 2.2 上传件为什么不放工作区外面

放外面（像 skills/artifacts 那样）的话，agent 的文件工具**看不见**它 ——
用户传了文件，agent 却读不到，那这个功能就没意义。

放工作区里，agent 用现有的 `read_file` / `grep` / `glob` 直接就能处理，
**不需要新增任何 agent 能力**。这是最小改动。

代价：agent 能改/删用户的原始上传件。对 code agent 来说这通常无所谓
（用户就是让 agent 改它），但**原件被改掉后用户没法拿回原始版本** ——
所以上传接口要同时返回原始文件的信息（名字、大小、哈希），让用户知道
自己传的是什么。

## 3. 存储布局

```text
workspace_root/
  └─ <thread_id>/                 ← 会话工作区（一个会话一份）
       ├─ uploads/                ← 用户上传件
       │    └─ 20261102_143000_需求说明.pdf
       ├─ src/ app/ ...           ← agent 的工作产物（它写哪就在哪）
       └─ AGENTS.md               ← 工作区说明

.artifacts/                       ← 工作区**外面**
  └─ <thread_id>/
       ├─ conversation_history/   ← 被压缩掉的对话历史（不给下载）
       ├─ large_tool_results/     ← 太大的工具输出（不给下载）
       └─ blobs/                 ← 二进制外置（不给下载）
```

**为什么上传件还要带时间戳前缀**：同一个会话里用户可能传两次同名文件。
带时间戳就不会互相覆盖，也不会让 agent 读到"上次那个"。

## 4. 接口

### 4.1 上传

```http
POST /api/v1/files?thread_id=t_20261102_xxx
Content-Type: multipart/form-data

（文件本体）
```

**用 `multipart/form-data` 而不是 JSON** —— 文件是二进制，base64 编码会膨胀
33%，大文件尤其明显。`python-multipart` 已经是依赖了（见 `pyproject.toml`）。

响应：

```json
{
  "code": 200,
  "data": {
    "path": "/uploads/20261102_143000_需求说明.pdf",
    "filename": "需求说明.pdf",
    "size": 245760,
    "sha256": "…",
    "uploaded_at": "2026-11-02T14:30:00Z"
  }
}
```

**返回虚拟路径**（`/uploads/...`）而不是宿主路径 —— 前端拿它去跟 agent 说
"看这个文件"，agent 用文件工具也能直接读。

### 4.2 列出工作区文件

```http
GET /api/v1/files?thread_id=t_20261102_xxx
```

返回工作区里的文件树（上传件 + 工作产物），带大小、修改时间、是否目录。
**不含 `.artifacts/`**。

### 4.3 下载

```http
GET /api/v1/files/download?thread_id=t_20261102_xxx&path=/uploads/xxx.pdf
```

按虚拟路径下载。路径解析走 `FilesystemBackend` 的 `virtual_mode` ——
`..` 穿越会被拒（实测 `ValueError: Path traversal not allowed`）。

### 4.4 删除

```http
DELETE /api/v1/files?thread_id=t_20261102_xxx&path=/uploads/xxx.pdf
```

### 4.5 批量下载（打包）

```http
GET /api/v1/files/archive?thread_id=t_20261102_xxx
```

返回 zip。**为什么需要**：agent 改完一个项目有几十个文件，用户要的是"打包
下载"，不是一个一个点。

用**流式 zip**（`zipfile` 边写边输出），不把整个 zip 读进内存 ——
工作区可能有几百 MB。

## 5. agent 怎么知道上传件在哪

用户传完文件，agent 未必知道。要在**下一轮上下文**里告诉它。

这正好是上下文模块的活 —— 加一个「上传件」块：

```xml
<uploaded_files>
用户上传了这些文件（按需用 read_file 读取）：
- /uploads/20261102_143000_需求说明.pdf （245 KB）
</uploaded_files>
```

**放进上下文而不是让前端转述**：用户上传完直接说"按这个需求改代码"是
最自然的交互，让他自己贴路径是多余的摩擦。

优先级：**高于记忆目录**（那是长期记忆，这个是本轮的工作材料）。

## 6. 大文件与小文件

| 情况 | 处理 |
| --- | --- |
| 上传 > `MAX_UPLOAD_MB`（默认 50MB） | 拒绝，明确报大小上限 |
| agent 读大文件 | `read_file` 有分页（`offset`/`limit`），`max_file_bytes`（默认 200KB）是单次读入上限 |
| 二进制文件 | `read_file` 返回 base64 —— **会撑爆上下文**。要提示模型用 `execute`/`run_python` 处理 |
| 大工具输出 | deepAgents 自动外置到 `.artifacts/large_tool_results/`（默认 20000 token 阈值） |

**上传件要不要先做体检**（扫描大小、类型、是否可执行）？第一版不做 ——
只做大小限制。理由：平台没有鉴权、用户身份不明，做了"安全扫描"也没地方报告
结果（给谁看？）。等有用户体系再说。

## 7. 保留期与清理

**文件跟着会话走** —— 会话删了，文件一起没。

但**平台现在没有会话管理模块**（没有会话表、没有删除接口 —— 记忆模块文档里
也记着这个缺口）。所以：

| 方案 | 说明 |
| --- | --- |
| A. 等会话管理模块 | 清理挂在"删除会话"上，语义最对；但要等会话管理做完 |
| B. 现在就做定时清理 | 按 `mtime` 清理 N 天没动过的工作区；简单但可能删掉用户还在用的 |
| C. 按容器回收顺带清 | 容器 30 分钟空闲就回收，但**工作区文件要留着** —— 回收容器不等于删文件 |

**倾向 A + C 组合**：容器回收照旧（它是执行环境，不是文件），
文件清理等会话管理模块。但**先加一个兜底**：工作区目录数超上限时，
按 `mtime` 回收最老的（跟容器的容量上限同一套思路）。

> ⚠️ **B 单独做是危险的** —— 用户可能两周没碰某个会话，但文件还要用。
> 时间不是"用户不再需要"的可靠信号。容量超限才是。

## 8. 安全

**这一节的每一条都因为平台没有鉴权而更要紧。**

1. **没有鉴权** —— 任何人知道 `thread_id` 就能：
   - 上传文件到别人的会话（塞东西）
   - 下载别人会话里的**所有文件**（含用户上传的需求文档、agent 改的代码）
   - 删除别人会话的文件
   - **thread_id 泄露了就是完全访问** —— 现在的 `thread_id` 由客户端生成，
     不够不可猜测。
   - **上线前必须补**。这是比记忆模块那条更严重的版本 —— 那里泄露的是
     "用户偏好"，这里是"用户的文件"。

2. **路径穿越** —— 下载/删除接口的 `path` 参数必须走 `virtual_mode` 的解析，
   `..` 要被拒。实测 `FilesystemBackend` 会抛 `ValueError: Path traversal
   not allowed`，但**接口层要把它转成 400 而不是 500**。

3. **软链接逃逸** —— `virtual_mode` 的 `resolve()` 会顺带抓出软链逃逸，
   但要在**下载时**再确认一次解析后的路径在工作区内（TOCTOU）。

4. **上传文件的类型** —— 不限制（agent 的工作区里本来就有任意文件），
   但**下载接口要设 `Content-Disposition: attachment`**，别让浏览器把
   HTML/SVG 当页面渲染（存储型 XSS）。

5. **大小限制** —— 上传要限大小，否则一个人能把磁盘写满。

## 9. 实施阶段

| 阶段 | 内容 | 前置 | 规模 |
| --- | --- | --- | --- |
| **F0** | 修 glob/grep 重复（**已完成**，实施时发现） | — | 小 |
| **F1** | 文件服务：上传 / 列表 / 下载 / 删除 + 路径安全 | — | 中 |
| **F2** | 上下文注入「上传件」块 | F1 | 小 |
| **F3** | 批量打包下载（流式 zip） | F1 | 中 |
| **F4** | 工作区容量上限 + 兜底回收 | — | 小 |

**建议顺序**：F0（已做）→ F1 → F2 → F3 → F4。

F1 是主体。F2 决定 agent 能不能用上上传的文件。

### 9.1 F0：glob/grep 重复（实施时发现，已修）

做 F1 时实测发现：`CompositeBackend.glob` / `grep` 在 path 为 `"/"` 时搜
**默认后端 + 所有路由**。我们的默认后端（沙箱）与 route `"/"`（宿主
FilesystemBackend）**指向同一个工作区** —— 每个文件出现两次：

```text
glob('**/*') -> ['/a.py', '/a.py', '/b.md', '/b.md']
```

agent 用 glob 找产物时会看到一堆重复项。已在 `PlatformBackend` 里去重
（按 path + 行号），并加了回归测试。

## 10. 已知风险

1. **没有鉴权，文件接口等于裸奔**（见 §8.1）。这是本方案最大的风险，
   也是上线前的硬门槛。
2. **thread_id 不够不可猜测** —— 现在由客户端生成。要么加随机后缀，
   要么等鉴权。
3. **上传件 agent 能改** —— 用户拿不回原件。上传接口返回 sha256 与原始
   文件名，让用户知道传的是什么。
4. **工作区无限增长** —— agent 生成的产物会一直堆着。靠 F4 的容量上限兜底。
5. **大 zip 的内存占用** —— 用流式 zip，别整个读进内存。

## 13. 已知会踩的坑

1. **别用 JSON 传文件** —— base64 膨胀 33%。用 `multipart/form-data`。

2. **别让下载接口直接返回宿主路径的文件** —— 必须走 `virtual_mode` 解析，
   否则 `path=/../../etc/passwd` 就能读系统文件。

3. **别把 `.artifacts/` 暴露给下载接口** —— 里面有对话历史。

4. **下载要设 `Content-Disposition: attachment`** —— 否则浏览器会把
   上传的 HTML/SVG 当页面渲染。

5. **zip 要流式输出** —— 工作区可能几百 MB，整个读进内存会 OOM。

6. **别忘了 `glob` 的重复**（F0）—— 默认后端与 route `"/"` 指向同一个目录，
   框架的聚合逻辑不会去重。
