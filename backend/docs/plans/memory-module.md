# 记忆模块计划

> 状态：**未开始**（2026-11-01）
>
> 关联文档：[implementation/rag-architecture.md](../implementation/rag-architecture.md)（RAG 服务层，已实现）、
> [capability-followups.md](capability-followups.md)（能力层待办）

记忆模块是 RAG 服务层的**消费者**：长期记忆落在 RAG 上，短期记忆不进 RAG。

结构是**两层**，不要再加第三层：

| 层 | 范围 | 落在哪 | 状态 |
| --- | --- | --- | --- |
| **短期记忆** | 会话内（一个 thread 内） | 进程内 / 会话状态 | ⬜ 未开始 |
| **长期记忆** | 跨会话 | RAG 的 `rag_document` | ⬜ 未开始 |

> ⚠️ 命名和分层改过好几轮：不要"情景记忆"、不要"知识"那一层、不要三层。
> 就是上面这两层。

## 1. 阶段

| 阶段 | 内容 | 状态 |
| --- | --- | --- |
| **M0** | 记忆模块骨架（短期 / 长期两层） | ⬜ 未开始 |
| **M1** | 长期记忆落在 RAG 上 + `memory_search` 能力 | ⬜ 未开始 |

### M0：骨架

- 两层的存储接口先定下来：`MemoryStore` 协议，短期一个实现（进程内）、
  长期一个实现（走 RAG）。
- 记忆条目的结构：内容 + 元数据（来源会话、时间、标签、强度）。
- 短期记忆的生命周期挂在 thread 上，会话结束即失效 —— 跨请求保持的能力
  （原先 `change_directory` 用过类似的 `.qzd_state/<工作区名>.json` 落法，
  那个能力已经删掉了，落法可以参照思路。）

### M1：长期记忆 + 检索能力

- 长期记忆写进 RAG 集合（一个专用的记忆集合，向量化配置跟其它集合分开）。
- 提供 `memory_search` 能力，走能力层的七阶段流水线 —— **不是**绕过执行层直接查库。
- 记忆的写入也要走能力层（模型提议"这条值得记"，经过风险评估和审批后再落库）。

**RAG 侧要注意**：集合的向量化配置是**锁死**的（模型名 + 维度记在集合上）。
换嵌入模型 = **重建集合**，不是改个字段。记忆集合如果选了某个模型，
以后换模型就得把记忆重新灌一遍。

## 2. 前置改动：风险模型拆维度

**这是 M1 的前置**，不先做完，`memory_search` / `rag_search` 会被治理层拦死。

**问题**：这两个能力打的是**平台配置的向量化端点**（目标固定、由平台配好），
不是模型自己指定的地址。但能力层的风险模型目前只有一个 `open_world` 标记 ——
联网就被判成 `network` 风险，`balanced` 信任模式下**每次检索都要人工审批**。

**要做的事**：把风险模型从"一个维度"拆成两个正交维度。

| 字段 | 取值 | 含义 |
| --- | --- | --- |
| `egress_target` | fixed / model-controlled | 连到哪里是平台定的还是模型定的 |
| `egress_data` | yes / no | 有没有把数据发出去 |

平台自配的向量化端点 = `fixed` + `yes` → 不是模型能操控的出口，
不该按 `network` 风险拦。

**影响面**：

- 这是对**已发布内置能力声明的破坏性变更** —— 所有走网络的内置能力
  （`web_fetch`、`web_search`）都要补这两个字段。
- 要配迁移：加列 + 回填 + 改 `registration/policy.py` 的风险判定 +
  更新内置能力的出厂声明（`registration/builtin/`）。
- 判定逻辑改成"两个维度组合"，而不是现在的单一 `open_world` 标记。

**顺序**：风险模型拆维度 → M0 → M1。不要先做 M1 再补，否则中间那段
每次检索都要求人工审批的状态会被当成 bug 反复排查。
